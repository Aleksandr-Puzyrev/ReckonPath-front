# Соглашения API: что нужно от бэкенда

Для разработчика бэкенда Reckon Path. Мобильный клиент перешёл на соглашения бэкенда (решение 0047): обёртка `{success, data}`, ошибки `{success: false, code, message, errors, data}`, snake_case, коды ошибок бэкенда, путь `/api/v1`. Клиент сам разворачивает ответы и переводит ключи, менять формат бэкенду не нужно.

Остались три вещи, которые клиент сделать не может, и список кодов для ещё не сделанных функций. Недостающие эндпоинты и отличия в поведении — в реестре `docs/backend-discrepancies.md` (строки вида A1, K14).

## 1. Идемпотентность — обязательно (G6)

Клиент отправляет `Idempotency-Key: <uuid>` на каждый POST/PUT/PATCH/DELETE. Ключ создаётся один раз на действие игрока и повторяется, когда запрос уходит заново после обрыва сети или таймаута.

Нужно:

* Хранить 24 часа: (пользователь, `Idempotency-Key`) → хеш тела запроса + сохранённый ответ (статус и тело).
* Повтор с тем же ключом и тем же телом → вернуть сохранённый ответ, действие повторно не выполнять.
* Тот же ключ с другим телом → `409`, код `idempotency_mismatch`.

Без этого повтор после обрыва выполнит действие дважды: например, «+3 хода» спишет изумруды два раза, покупка пройдёт дважды.

## 2. `X-Request-Id` — желательно (G16)

Клиент отправляет `X-Request-Id: <uuid v7>` в каждом запросе. Нужно принять его (если это валидный UUID), писать в логи и вернуть тот же в ответе; свой генерировать, только если заголовка нет. По нему ошибки из Sentry на клиенте сопоставляются с логами сервера. Сейчас бэкенд игнорирует заголовок и генерирует свой.

## 3. `Date` в ответе — не убирать

Клиент синхронизирует часы по стандартному заголовку `Date` ответа (Go `net/http` ставит его сам). Если когда-нибудь появится заголовок `X-Server-Time` (RFC 3339 UTC, с миллисекундами), клиент перейдёт на него — это точнее.

## 4. Язык

Клиент отправляет `Accept-Language: ru | en` (и `X-Locale` с тем же значением). Тексты `message` и серверные тексты стоит отдавать на этом языке — сейчас тексты техработ и обновления только русские (C7).

## 5. Коды ошибок

Каталог клиента — коды бэкенда как есть (lower snake_case). Клиент уже понимает все коды, которые сейчас отдаёт бэкенд. Особенности, на которые клиент рассчитывает:

* `invalid_refresh_token`, `refresh_token_reused`, `session_revoked` — клиент считает сессию отозванной и начинает заново. Для истёкшего access-токена — `unauthenticated` или `invalid_token` (клиент делает refresh и повторяет запрос).
* На `/auth/login`, `/auth/register*`, `/auth/oauth/*` клиент не делает refresh при 401 — там 401 значит неверные данные.
* `not_enough_gems` и `insufficient_funds` — клиент показывает лист «Как заработать». Ему нужно знать, сколько не хватает: `data: {need: <число>}` в ошибке.
* `maintenance` (503) — экран техработ; `app_update_required` (426) — экран обновления; `banned` (403) — экран бана с `data: {scope: "all" | "arena", until, reason}`.
* Поля с ошибками валидации — в `errors`, ключи — имена полей запроса.

Для функций, которых в бэкенде ещё нет, клиент уже использует эти коды. Просим взять их же:

| Код | HTTP | Когда | `data` |
| --- | --- | --- | --- |
| `banned` | 403 | Бан | `scope`, `until`, `reason` |
| `forbidden` | 403 | Нет прав | — |
| `not_found` | 404 | Сущность не найдена (можно и свои `*_not_found`) | — |
| `idempotency_mismatch` | 409 | Тот же ключ, другое тело | — |
| `already_owned` | 409 | Предмет уже есть | — |
| `not_owned` | 409 | Предмета нет в инвентаре | — |
| `in_match` / `already_queued` | 409 | Уже в матче / в очереди | `match_id`, `endpoint` для `in_match` |
| `map_active` | 409 | Нельзя удалить активную карту | — |
| `nick_taken` | 409 | Ник занят | — |
| `email_taken` | 409 | E-mail занят | — |
| `account_conflict` | 409 | Способ входа привязан к другому аккаунту | краткая сводка того аккаунта |
| `invalid_credentials` | 401 | Неверный логин или пароль | — |
| `insufficient_funds` | 422 | Не хватает валюты | `need` |

Тот же стиль — для сообщений WebSocket игрового сервера (арена): snake_case, коды ошибок из таблицы, а для хода — `not_your_turn`, `cell_revealed`, `cell_rock`, `stale_turn`, `match_over`.

Новый код, которого нет ни в бэкенде, ни в таблице, сначала согласуется с клиентом.

## 6. Формат данных

Клиент читает любой формат RFC 3339, но лучше отдавать время в UTC с `Z` (сейчас время сериализуется в часовом поясе процесса, G8).

## 7. Удалённый конфиг и стартовые данные

Клиент берёт версию и техработы из `/version` и `/maintenance` (решение 0049). Остальное, что по ТЗ (Часть 7 §3, `GET /bootstrap`) приходит при старте, в бэкенде отсутствует, и клиент пока берёт это из моков:

* `config` — удалённые настройки, ключи ровно в таком виде (с точками, клиент их не переводит): `arena.maxTurns`, `ads.interstitial.everyN`, `ads.interstitial.minIntervalSec`, `ads.interstitial.minLevel`, флаги функций вида `features.events`;
* `ads_network` — рекламная сеть;
* `content_version` — версия контента кампании;
* `day_key`, `next_day_at` — ключ текущего дня и начало следующего (для «Пеленга дня»).

Нужен эндпоинт с этими полями — `GET /bootstrap` или любой другой, согласуем.

## 8. Профиль

* Хранить язык пользователя: принимать `PATCH /me {locale: "ru" | "en"}` (сейчас 422 на неизвестное поле). Язык нужен для пушей и серверных текстов; пока клиент меняет его только на устройстве (решение 0052 #3).
* Отмена удаления: `POST /me/restore` в течение 30 дней и не закрывать сессии сразу при `DELETE /me` — тогда клиент вернёт экран «Аккаунт будет удалён … · Отменить удаление» (ТЗ Часть 1 §7.6). Сейчас клиент после удаления сразу становится гостем.
* Поля `GET /me`, без которых клиент не может перевести профиль на бэкенд: `wallet {emeralds, coins}`, `level`, `xp`, `xp_to_next`, `arena {trophies, league, division}`, `loadout`, `flags.deletion_scheduled_at`. До этого `GET /me` у клиента на моках.

## 9. Базовый путь

Остаётся `/api/v1`, клиент указывает базовый URL `https://<host>/api`. Сообщите хосты стенда и прода.
