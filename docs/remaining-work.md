## План работ

Правило для всех шагов: если у бэкенда есть эндпоинт, сначала запускаем `check-backend` и подключаем его вместе с клиентской задачей (маршрут добавляется в `BACKEND_ROUTES`). Если эндпоинта нет, делаем экран по макету на моках и записываем, что нужно от бэкенда, в `backend-handoff/backend-backlog.md`.

### Итерация 3 — этап 5 на моках (план этапа согласовать до начала, 0039 #4)

Друзья и вызовы → лидерборды → события → пуши (категории, баннер 25.3, переходы по нажатию). Каждый раздел — отдельная задача: моки + записи в бэклог бэкенда. Разделы независимы, их можно раздать параллельным исполнителям (`decompose-task`), если общие контракты в `contracts/` готовы.

### Итерация 4 — этап 6, по мере появления ключей

Порядок по зависимостям: сборка (`eas.json`, `app.config.ts`, bundle id) → Sentry и аналитика → реклама (Yandex, AdMob, UMP) → VK ID и Яндекс ID → App Integrity → звук и анимации → ссылки и шаринг → Maestro E2E. Без сборки на EAS и bundle id остальные пункты на устройствах не проверить, поэтому она первая.

### Параллельно — перенос с моков на бэкенд

Идёт отдельной дорожкой, по мере появления эндпоинтов из бэклога (раздел 4). Перед каждым переносом — `check-backend`. Самые важные для «рабочего приложения»: `/bootstrap` и полный `GET /me` (профиль, кошелёк, уровень), затем синхронизация кампании (K2: `/attempts:batch` против `/campaign/offline/sync` — нужно решение), дейли, арена (REST + WebSocket — на бэкенде её нет совсем).
